# CI/CD: Build & publish the Android app to Google Play

> Implementation plan. The companion **[codex-handoff.md](./codex-handoff.md)** turns this
> into step-by-step execution instructions for an implementing agent. The manual process this
> automates is **[../publishing-android.md](../publishing-android.md)**.

## Context

`voice-driven-checklist` is an **Expo SDK 55 / RN 0.83** app (`com.mbuchoff.voicechecklist`) that
ships to Google Play today via a **fully manual, local-Mac process** documented in
`docs/publishing-android.md`. There is no CI/CD, no Fastlane, no EAS. We want a GitHub Actions
pipeline that, on every push to `main`, builds a signed `.aab` and uploads it to the
**Internal testing** track — using the **GitHub Actions run number as the Android `versionCode`**.

After this pipeline is enabled, it is the only process that allocates new Play version codes and
uploads releases. A human-requested release uses `workflow_dispatch`; locally-built bundles must not
be uploaded independently because their version code is outside the workflow's sequence.

Two facts shape the design:

- **`android/` is gitignored and regenerated by `expo prebuild`.** So `versionCode` and the release
  signing config live in *generated* files. They must be re-injected on every CI run — which means an
  Expo **config plugin** (for signing) and a **dynamic `app.config.js`** (for `versionCode`), not
  hand edits to `android/app/build.gradle`. `docs/publishing-android.md` §2 already anticipates this
  ("Worth pinning them into a config plugin later").
- **`versionCode`s 1 and 2 are already used on Play.** GitHub `run_number` starts at 1, so the first
  two workflow runs (codes 1, 2) will be **rejected at upload** and only runs ≥ 3 will publish —
  matching the "throw away the first two runs" expectation. Deleting the old releases does *not* free
  codes 1/2 (Play permanently reserves used version codes); letting runs 1–2 fail is the reliable
  path. Optional alternative if you'd rather not have two red runs: add a constant offset
  (`versionCode = run_number + 2`). This plan uses `run_number` directly, as requested.

### Decisions (confirmed)

| Question | Choice |
|---|---|
| Trigger | **Push to `main`** (plus `workflow_dispatch` for manual test runs) |
| Play track | **Internal testing**, `status: completed` |
| Upload auth | **Google Play service-account JSON**, provided as a GitHub secret |
| versionCode | **`github.run_number`** |
| Signing injection | **Expo config plugin** (mirrors `docs/publishing-android.md` §2) |
| Release authority | **GitHub Actions only**; manual releases use `workflow_dispatch` |

## Prerequisites (one-time, human-owned — outside this repo)

1. **Service account for Play upload:** create a service account in Google Cloud → enable the
   *Google Play Android Developer API* → in Play Console (Users & permissions) invite the
   service-account email and grant release access to this app → download the JSON key.
2. **Add GitHub Actions secrets** (repo → Settings → Secrets and variables → Actions):
   - `ANDROID_KEYSTORE_BASE64` — `base64 -w0 "play-store-voice-checklist-upload - passphrase is <redacted>.jks"`
   - `ANDROID_KEYSTORE_PASSWORD` — *the passphrase embedded in the keystore filename* (from your password manager)
   - `ANDROID_KEY_ALIAS` — `upload`
   - `ANDROID_KEY_PASSWORD` — *same passphrase as the store password*
   - `PLAY_SERVICE_ACCOUNT_JSON` — full contents of the service-account JSON
3. **Declare the microphone foreground service in Play Console:** under **App content → Foreground
   service permissions**, select **Microphone** and the background-audio/voice-command use case.
   Explain that listening starts only after the user starts a checklist, voice commands are processed
   without recording or retaining audio, an ongoing notification provides a Stop action, and deferring
   or interrupting the service disables hands-free checklist control. Supply a publicly accessible
   demo video showing the start action, ongoing notification, working voice commands, and Stop action.
4. The app listing already exists on Play with ≥ 1 manual upload (codes 1, 2), so Google's
   "first upload must be via Console" gate is already cleared — API uploads for codes ≥ 3 are accepted.

## Changes

### 1. `plugins/withReleaseSigningConfig.js` (new) — release signing via config plugin

Follows the style of the existing `plugins/withNotifeeMicrophoneForegroundService.js`. Uses
`withAppBuildGradle` from `expo/config-plugins` to transform the generated `android/app/build.gradle`
with two whitespace-tolerant, idempotent replacements (throw loudly if an anchor isn't found, like the
Notifee plugin does):

**a. Add a `release` signingConfig** after the `debug` one (anchor: the debug block's
`keyPassword 'android' } }` closing before `buildTypes {`):

```groovy
        release {
            if (project.hasProperty('VOICE_CHECKLIST_UPLOAD_STORE_FILE')) {
                storeFile file(VOICE_CHECKLIST_UPLOAD_STORE_FILE)
                storePassword VOICE_CHECKLIST_UPLOAD_STORE_PASSWORD
                keyAlias VOICE_CHECKLIST_UPLOAD_KEY_ALIAS
                keyPassword VOICE_CHECKLIST_UPLOAD_KEY_PASSWORD
            }
        }
```

The `hasProperty` guard means local/dev prebuilds without the gradle props still succeed
(debug signing), exactly as the manual doc describes.

**b. Repoint the `release` build type** from the debug key to the new release config. The release
buildType's `signingConfig signingConfigs.debug` is uniquely preceded by the comment
`// see https://reactnative.dev/docs/signed-apk-android.` — anchor on that pair and change only that
line to `signingConfig signingConfigs.release` (leaving the `debug` buildType's identical line
untouched).

Register it in **`app.json`** by appending `"./plugins/withReleaseSigningConfig"` to the
`expo.plugins` array (after `"./plugins/withNotifeeMicrophoneForegroundService"`).

### 2. `app.config.js` (new) — `versionCode` from the run number

Expo reads `app.json` first and passes it to a dynamic `app.config.js`. Export a function that spreads
the static config and overrides only the Android `versionCode` from an env var, falling back for local
builds:

```js
module.exports = ({ config }) => ({
  ...config,
  android: {
    ...config.android,
    versionCode: process.env.ANDROID_VERSION_CODE
      ? Number(process.env.ANDROID_VERSION_CODE)
      : config.android?.versionCode ?? 1,
  },
});
```

`expo prebuild` then propagates this into `android/app/build.gradle`. `app.json` stays the untouched
base config (no mutation, clean working tree).

### 3. `.github/workflows/android-release.yml` (new) — the pipeline

```yaml
name: Android Release
on:
  push:
    branches: [main]
  workflow_dispatch:            # manually requested releases (run_number still increments)
concurrency:                    # retain pending releases and allow one upload at a time
  group: android-release
  queue: max
permissions:
  contents: read
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 17, cache: gradle }
      - uses: android-actions/setup-android@9fc6c4e9069bf8d3d10b2204b1fb8f6ef7065407 # v3.2.2
      - run: yes | sdkmanager "ndk;27.1.12297006" "cmake;3.22.1" "platforms;android-35" "build-tools;35.0.0"
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test
      - name: Decode upload keystore
        env:
          ANDROID_KEYSTORE_BASE64: ${{ secrets.ANDROID_KEYSTORE_BASE64 }}
        run: echo "$ANDROID_KEYSTORE_BASE64" | base64 -d > "$RUNNER_TEMP/upload.jks"
      - name: Prebuild (inject versionCode + signing)
        env:
          ANDROID_VERSION_CODE: ${{ github.run_number }}
        run: npx expo prebuild --platform android --no-install
      - name: Build signed AAB
        working-directory: android
        env:                    # ORG_GRADLE_PROJECT_* -> gradle project properties (kept out of argv/logs)
          ORG_GRADLE_PROJECT_VOICE_CHECKLIST_UPLOAD_STORE_FILE: ${{ runner.temp }}/upload.jks
          ORG_GRADLE_PROJECT_VOICE_CHECKLIST_UPLOAD_KEY_ALIAS: ${{ secrets.ANDROID_KEY_ALIAS }}
          ORG_GRADLE_PROJECT_VOICE_CHECKLIST_UPLOAD_STORE_PASSWORD: ${{ secrets.ANDROID_KEYSTORE_PASSWORD }}
          ORG_GRADLE_PROJECT_VOICE_CHECKLIST_UPLOAD_KEY_PASSWORD: ${{ secrets.ANDROID_KEY_PASSWORD }}
        run: ./gradlew bundleRelease --no-daemon
      - uses: actions/upload-artifact@v4
        with:
          name: app-release-${{ github.run_number }}
          path: android/app/build/outputs/bundle/release/app-release.aab
      - name: Upload to Play (internal)
        uses: r0adkll/upload-google-play@e738b9dd8f2476ea806d921b64aacd24f34515a5 # v1.1.5
        with:
          serviceAccountJsonPlainText: ${{ secrets.PLAY_SERVICE_ACCOUNT_JSON }}
          packageName: com.mbuchoff.voicechecklist
          releaseFiles: android/app/build/outputs/bundle/release/app-release.aab
          track: internal
          status: completed
```

Notes: lint/typecheck/test gate the release (matches repo test culture — drop them if undesired). The
artifact upload means even a run whose Play upload is rejected (codes 1/2) still yields a downloadable
`.aab`. `queue: max` prevents a newer pending run from replacing an older pending run and serializes
the releases; GitHub queues at most 100 pending runs and does not formally guarantee dispatch order.
Pin third-party actions to commit SHAs for supply-chain safety.

### 4. `.gitignore` (edit) — guard the new secret file

Add an ignore for a locally-saved service-account key, e.g. `*service-account*.json`, so it can't be
committed by accident. (`*.jks` is already ignored.)

## Security follow-ups (recommended)

- The upload keystore's passphrase is **in the filename in plaintext**. After base64-ing it into
  `ANDROID_KEYSTORE_BASE64`, rename the local file to drop the passphrase
  (e.g. `voice-checklist-upload.jks`) and keep the passphrase only in your password manager + the
  GitHub secret. It's gitignored (not committed) but plaintext-in-filename leaks via
  backups/screen-shares/`git add -f`.
- Never `echo` secrets in workflow steps; the `ORG_GRADLE_PROJECT_*` env approach above keeps them out
  of `argv` and `gradle.properties`.

## Verification

**Local (fast, no Play):**

- `npm test` — the three new test files pass; full suite stays green.
- `ANDROID_VERSION_CODE=999 npx expo prebuild --platform android --no-install --clean`, then confirm
  in the regenerated `android/app/build.gradle`: `versionCode 999`, the `release` signingConfig block
  exists, and the release buildType shows `signingConfig signingConfigs.release`.
- Optional signed-build check: from `android/`, run `./gradlew bundleRelease --no-daemon --no-parallel`
  with the four `ORG_GRADLE_PROJECT_VOICE_CHECKLIST_UPLOAD_*` env vars set (store file = absolute path
  to the `.jks`, alias `upload`, store/key password = the keystore passphrase), then
  `jarsigner -verify -verbose -certs android/app/build/outputs/bundle/release/app-release.aab | head`
  shows the `upload` cert. (Per `AGENTS.md`, gradle may OOM in the dev container — best run on the CI
  runner or a Mac.)

**CI end-to-end:**

- After adding all five secrets and completing the foreground-service declaration, trigger via
  **Run workflow** (`workflow_dispatch`) or push to `main`.
- A workflow run whose `run_number` is already present in Play builds/signs/artifacts successfully
  but fails the upload with a duplicate-versionCode error. Trigger a later run; do not allocate or
  upload a competing version code manually.
- Confirm the successful run's version code in **Play Console → Testing → Internal testing** and
  install via the internal-testing opt-in link.
- After CI cutover, request every release through a push to `main` or **Run workflow**. Do not allocate
  a separate version code and upload a locally-built bundle.
- Monitor CI without `checks:read` scope (per environment notes):
  `gh api "repos/mbuchoff/voice-driven-checklist/actions/runs?head_sha=<sha>" --jq '.workflow_runs[] | {name, status, conclusion}'`.

**Observed branch validation (July 2026):**

- Runs 1 and 2 built, signed, and preserved their artifacts, then Play rejected their already-used
  version codes.
- Runs 3 and 4 built, signed, preserved their artifacts, authenticated to Play, and uploaded their
  AABs, then Play rejected the edit commit because the foreground-service declaration had not been
  submitted.
- Implementation is not live-verified until a later GitHub Actions run completes successfully and
  the resulting version code appears on the Internal testing track.
